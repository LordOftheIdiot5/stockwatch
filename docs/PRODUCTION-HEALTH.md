# Production health monitor
Independent hourly read-only production checks. Manual dispatch after releases. Checks selected HTML routes, canonical and robots directives including HTTP X-Robots-Tag, sitemap, coverage/price loss, snapshot age, source health, SEC index + two issuer samples, GLEIF snapshot, D1 archive count. Baselines fixed at approved 500 listings, 139 monitored, 152 priced, 29,155 SEC facts, 17 GLEIF matches, 1,640 D1 records. Revisit intentionally changed baselines through reviewed PR; known missing prices are metrics, not failures. One GitHub incident per changed critical signature; optional Telegram using existing credentials; no secrets logged. Warnings retained in diagnostics, no automatic code changes. GitHub scheduled runs can be delayed and are not real-time. Static fetch is not interactive browser coverage; existing visual audit remains separate; browser canaries and full 50 SEC per-file checks are follow-up. PR validation records production findings without creating issues or requiring production cutover success. First manual run after merge confirms notification permissions and production state.
## Telegram and deployment resilience
Use the existing repository Actions secrets TELEGRAM_BOT_TOKEN and TELEGRAM_CHAT_ID. Do not put the token or recipient ID in public code, variables, data, URLs or Pages assets. Create the operations bot with the official @BotFather and start the bot from the intended private chat or private operations group. Use manual Test private Telegram alerts workflow after adding secrets; no third-party chat-ID bot needed. Keep the public Nordl business account independent; publish only its confirmed public username, not private phone, chat ID or operations bot credentials. For a human business contact use a separate business-number account with restrictive phone/contact sync settings; for stronger operator anonymity a separate public contact bot is an alternative but would need its own token and routing. Do not publish placeholder handles. Both Pages workflows now poll artifact metadata for up to about one minute after upload before invoking deploy-pages. This mitigates observed temporary artifact visibility failure but does not guarantee GitHub availability. A failed gate remains a deployment failure for investigation. No automatic code modifications.
